── EXPORT UI JITTER — REAL CAUSE ──

Your diagnosis was close but not quite right. Here is exactly what happens:

The export runs on a background thread in C++ (crypto_bridge.cpp), but the
progress updates come back to the Flutter UI thread via MethodChannel. Each
time a file finishes exporting, ExportCoordinator yields an ExportProgress
event, and the dialog calls setState() to update the file counter. That
setState() triggers a Flutter frame rebuild.

The jitter during export has two overlapping causes:

1. BCrypt CPU burst starves the Flutter raster thread briefly.
   BCrypt with AES-NI runs at ~3,000 MB/s on your i5-12450H. For a 3 MB
   image that is under 1 ms of CPU time. But you have 224 files. The export
   loop does: decrypt (BCrypt on detached thread) → await → addFile to ZIP
   (Dart, on the main isolate, which calls ZipFileEncoder — that is CPU
   work on the UI thread) → setState → repeat. The ZipFileEncoder.addFile()
   call runs DEFLATE compression synchronously on the Dart isolate. For
   JPEG images it barely compresses (JPEGs are already compressed), but it
   still reads and copies ~3 MB of file data per image on the UI thread.
   At 224 files over ~30 seconds that is one UI-thread file-copy every
   ~130 ms. Flutter targets one frame every 8.3 ms (120 Hz). A 130 ms sync
   I/O burst on the UI thread drops ~15 frames in a row — visible as jitter.

2. MethodChannel result delivery on the platform thread.
   BCrypt runs on a std::thread. When it finishes, it calls
   result->Success(...) from that thread. The Flutter engine posts this
   back to the platform thread, then delivers it to the Dart isolate. If
   the Dart isolate is busy doing ZipFileEncoder work (file copying) at that
   moment, the MethodChannel delivery queues up. When Dart finally processes
   the queue in one go it triggers multiple setState() calls in quick
   succession, causing frame bursts.

- For this issue what we can do is we can create function to handle the queue, rather than accumulating the setState request we can keep a count of how many files have been decrypted and when it gets it cpu time, rather than running all queued up requests, we just increase the file count counter on UI but the count we have taken and dump the setState requests to avoid a re-render. Though I have no correct idea of how the process works so find a solution as you sees fit best for this problem that won't cause issue in any sense or break anything.

So the sequence is:
  BCrypt decrypts 3 MB in ~1 ms (background C++ thread, fast, no UI impact)
  ↓
  MethodChannel delivers result to Dart isolate
  ↓
  ZipFileEncoder.addFile() runs on Dart isolate: reads 3 MB temp file,
  runs DEFLATE (no-op for JPEG), writes to ZIP (~5–20 ms on NVMe)  ← UI THREAD BLOCKED HERE
  ↓
  setState() → frame rebuild → spinner animates (or stutters if rebuild
  takes longer than 8 ms)
  ↓
  repeat for next file

The spinner jitter is exactly this: the UI thread is blocked by
ZipFileEncoder for ~5–20 ms per file, which drops frames. With 224 files
at ~130 ms average gap the jitter is periodic and noticeable.

This does NOT mean the export is broken. The export itself runs correctly
and fast. The jitter is purely visual — the spinner animation stutters
because the UI thread is competing with ZIP encoding work.

How it could be fixed (not doing this now, just informational):
  Move ZipFileEncoder.addFile() to a compute() isolate or a background
  Isolate.run() call. That would free the UI thread completely and the
  spinner would be perfectly smooth throughout. This is a Phase 6 polish
  item — the current architecture is functionally correct and fast, just
  not frame-perfect during encoding.

Your task manager reading (930 MB for jtkbinaries = the JetBrains IDE
process, not Local Vault) is correct — the app itself uses well under
200 MB RAM during export since we decrypt and zip one file at a time.


── PASSWORD SYSTEM — CONFIRMED ARCHITECTURE ──

The password system is correct and uses the new secure DEK architecture.
Here is exactly what happens when you enter your password (traced from
auth_session.dart):

1. AuthSession.unlock(password) is called.

2. CredentialRepository.hasEnvelope() checks flutter_secure_storage for
   the Phase 5 key envelope — it exists (you're past first-run).

3. The envelope is loaded: it contains your KEK salt, iteration count
   (200,000), and the wrapped DEK (your 32-byte vault encryption key
   encrypted under a key derived from your password).

4. DartCryptoEngine.deriveKek(password, salt, 200000) runs in
   Isolate.run() — completely off the UI thread. This runs PBKDF2-HMAC-SHA256
   for 200,000 iterations. On your i5-12450H in release mode this takes
   ~100–200 ms. The UI stays responsive (spinner animates).

5. DartCryptoEngine.unwrapDek(wrappedDekBytes, tagBytes, nonceBytes, kek)
   runs AES-256-GCM to decrypt your DEK using the derived KEK. If the
   password is wrong, the GCM tag fails and throws AuthenticationFailure
   immediately — no garbage bytes returned.

6. The 32-byte DEK is stored in AuthSession.current.dek (in-memory only,
   never written to disk in plaintext). The KEK is immediately zeroed.

7. Navigator pushes to the home screen.

What makes this more secure than the old system:
   Old: password was verified by PBKDF2 hash comparison only. The actual
   vault key (DEK) was stored in Windows Credential Manager in plaintext —
   anyone with access to the keystore could extract it without knowing the
   password.

   New: the DEK is wrapped (encrypted) by the KEK which is derived from
   your password. Without the correct password, the AES-256-GCM tag fails
   and the DEK cannot be recovered. The vault key is cryptographically
   bound to your password.

Conclusion: the password system is working exactly as designed. The quick
password check you noticed is because the envelope path skips the old
hash-based KDF verification round (one PBKDF2 call instead of two). The
GCM tag check replaces the hash comparison, so you get authentication in
a single KDF derivation.

ADDITIONAL PC ANSWER — setState queue throttle idea
═══════════════════════════════════════════════════

Your idea is correct in principle. The standard Flutter pattern for this
is called "coalescing" or "throttled setState" — you batch rapid progress
updates into a single rebuild rather than one rebuild per file.

Here is how it actually works and the right way to implement it:

The problem: ExportCoordinator.exportFolder() is an async* Stream. The
dialog does:
  await for (final progress in ...) { setState(() { _completedFiles = ...; }) }

Each file completion yields one event, which triggers one setState, which
schedules one frame rebuild. With 224 files completing every ~130 ms,
that is one rebuild every ~130 ms — not actually too many (Flutter can
handle 120/s). The real jitter is NOT from too many setStates. It is from
ZipFileEncoder blocking the UI thread for 5–15 ms between setStates.

So throttling setState alone would not fully fix the jitter. The root fix
is moving ZipFileEncoder off the UI thread (Phase 6). However your idea
does have value: it avoids unnecessary redraws when files complete very
fast (e.g. many small files).

The correct implementation — a "latest value wins" coalescer:

Instead of calling setState on every event, you track the latest progress
value and only rebuild when a frame is actually due:

  var _latestProgress = 0;
  var _latestTotal = 0;
  bool _pendingRebuild = false;

  void _onProgress(ExportProgress p) {
    _latestProgress = p.completedFiles;
    _latestTotal = p.totalFiles;
    if (_pendingRebuild) return;  // already one rebuild scheduled, skip
    _pendingRebuild = true;
    // Schedule rebuild on next frame — any further updates before the
    // frame fires are absorbed (they update the vars above but don't
    // schedule another rebuild).
    WidgetsBinding.instance.addPostFrameCallback((_) {
      if (mounted) setState(() {});
      _pendingRebuild = false;
    });
  }

This way if 10 files complete before the next frame (16 ms), you get
exactly one setState for all 10 — not 10 separate rebuilds. The counter
on screen shows the latest value (all 10 reflected at once).

This is a clean, safe Phase 6 improvement. No code changes now as
requested — just noting the exact right solution for when it is needed.

── BLACK SCREEN ON HIGHLY DETAILED / HIGH-RESOLUTION IMAGES ──

This is a known and expected behaviour specific to high-resolution images
on mobile, and it is different from the "black flash on Previous" bug
that was fixed on PC. Here is the exact cause on your device:

What happens:
  1. You tap Next (or Previous). _navigateTo(targetIndex) is called.
  2. _decryptAndCache(index) runs:
       → NativeCryptoEngine decrypts the file → temp file written to UFS
       → precacheImage(FileImage(file), context) is awaited
  3. precacheImage starts decoding the JPEG/WebP file into a raw bitmap
     in Flutter's image cache. For a high-resolution image (e.g. 4000×6000
     pixels, typical of a phone camera shot or manga scan), this decoded
     bitmap is ~4000 × 6000 × 4 bytes = ~91 MB.
  4. Flutter decodes images on a background thread (the image decoder runs
     in a separate isolate). But the FINAL step — uploading the decoded
     bitmap to the GPU as a texture — happens on the raster thread and
     requires one GPU frame to complete.
  5. precacheImage "completes" when the decode is done, but the GPU texture
     upload may still be in the raster thread queue. So when AnimatedSwitcher
     triggers the crossfade, the incoming _ImagePage widget renders
     Image.file(). Flutter draws the widget but the GPU texture is not
     yet fully resident for very large images — for one raster frame the
     GPU draws black/background because the texture is still uploading.

Why it only happens on "highly detailed" images:
  A 1080×1920 image = ~8 MB decoded texture → GPU upload takes <1 ms,
  texture is ready before the first rendered frame.
  A 4000×6000 image = ~91 MB decoded texture → GPU upload takes 5–30 ms
  depending on memory bandwidth (your Z9x has 22 GB/s LPDDR4X bandwidth)
  → the first rendered frame of the crossfade may arrive before the
  texture is fully uploaded → black for one frame.

Why PC doesn't have this:
  Your GT Book's GPU has higher memory bandwidth and processes the texture
  upload faster. Also desktop image files in your import were likely the
  same 224 JPEG images at 3 MB average, which decode to smaller bitmaps
  than full-resolution phone/manga scans.

Can it be fully fixed?
  Partially. The current code already does the right things (precacheImage
  awaited, gaplessPlayback: true). What remains is a limitation of Flutter's
  GPU upload pipeline on mobile — it cannot be fully prevented for very
  large images without either:
  a) Downscaling the image before display (ResizeImage to screen resolution)
     which is already done in OptimizedImageViewer but not in the main
     ImageViewerScreen. This trades quality for zero black flash.
  b) Adding a delay after precacheImage (a few frames) before triggering
     the crossfade, to allow the GPU upload to settle. This would add
     ~50–100 ms of extra wait before navigation but guarantee no black frame.

For your use case (manga/photos on a budget Snapdragon), option (a) is
the practical fix: cap the decode resolution to screen size. A 6.72-inch
1080×2408 screen does not benefit from decoding a 4000×6000 source at
full resolution — it gets downscaled to fit the screen anyway, so decoding
at screen resolution saves both RAM and GPU upload time.

This is a Phase 6 improvement. For now the black flash is one frame on
large images only, which you correctly identified as acceptable.
